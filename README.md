# volumetric-contact

[![ci](https://github.com/dvilelaf/volumetric-contact/actions/workflows/ci.yml/badge.svg)](https://github.com/dvilelaf/volumetric-contact/actions/workflows/ci.yml)
[Site and viewer](https://dvilelaf.github.io/volumetric-contact/) · [Paper source](paper/) · [Architecture](docs/architecture.md) · BSD-3-Clause

An engine-independent C++20 library of two elastic-foundation contact laws evaluated on the exact intersection of
triangle meshes: Gonthier's volumetric model and the same Winkler foundation integrated over the contact surface. It comes
with backends for Drake, Project Chrono and MuJoCo, and with a battery of 33 conforming- and patch-contact scenarios whose
answer is known analytically, used to compare the two laws with each engine's native contact. The laws are the continuation
of David Vilela's 2018 PhD thesis ([`docs/thesis-report.md`](docs/thesis-report.md)); the paper that describes them is in
[`paper/`](paper/).

## Quick start

Prerequisites: [Docker](https://docs.docker.com/engine/install/) and [just](https://github.com/casey/just) for the full
build (Drake, Chrono and MuJoCo live in one image, Ubuntu 24.04 inside); for the core alone, only CMake, Eigen 3.4 and a
C++20 compiler. The Python tools and the paper need [uv](https://docs.astral.sh/uv/).

```
just image            # build the Docker image (once; or pull it, below)
just build            # configure and build everything inside the container
just run disk         # one scenario: prints the metrics against the analytic reference
```

`scripts/dev.sh` pulls the image from ghcr.io/dvilelaf/volumetric-contact-dev the first time; `just image` builds it locally.
The engine-independent core is built and tested in CI on Linux (GCC), macOS (Apple Clang) and Windows (MSVC). `just` alone lists every recipe; the main ones:

| Recipe | What it does |
|---|---|
| `just image`, `just build` | the Docker image; configure and build in `build/` |
| `just test` | the unit tests (core and scenarios) |
| `just verify`, `just verify-full` | the quality checks of a change; every check plus a smoke run of every scenario |
| `just scenarios` | list the 33 scenarios |
| `just run SCENARIO [ENGINE] [CONTACT]` | one run, base variant (defaults: `chrono`, `distributed`; `CONTACT` may be `native:<model>`) |
| `just bench`, `just bench-quick`, `just timing`, `just stats` | the battery (hours; only with the owner's permission on a shared machine), its base variant, the timing pass (idle machine only), the statistics |
| `just viewer`, `just site-serve` | the trajectory viewer on `results/traj`; the assembled site |
| `just paper`, `just paper-check` | build the paper; check its derivations numerically |
| `just meshes`, `just lint`, `just py-test` | regenerate the meshes; ruff; the Python tests |
| `just core`, `just core-test`, `just example` | the core alone on the host, no Docker (next section) |

The recipes are thin wrappers: the scripts in `scripts/` are the source of truth (`scripts/dev.sh <cmd>` runs any command in
the container).

## Use it in your engine

The core builds on its own, without Docker or any physics engine, and installs as a CMake package:

```
just core             # builds and installs the core into build-core/prefix
just example          # builds examples/minimal against it and runs it
just core-test        # the core's unit tests on the host
```

which is, by hand:

```
cmake -S . -B build -DVOLCONTACT_BUILD_BENCHMARK=OFF -DVOLCONTACT_BUILD_TESTS=OFF && cmake --build build
cmake --install build --prefix /opt/volcontact      # then: find_package(volcontact CONFIG) → volcontact::core
```

`FetchContent` works too (`FetchContent_Declare(volcontact GIT_REPOSITORY https://github.com/dvilelaf/volumetric-contact)`,
then `target_link_libraries(app PRIVATE volcontact::core)`). [`examples/minimal`](examples/minimal) drops a box on a slab with no physics engine;
[`docs/integration.md`](docs/integration.md) explains the three calls an engine needs, how to add a backend and the
pitfalls; `core/include/volcontact/c_api.h` is a C interface for other languages.

## The laws and their baselines

All laws share the exact mesh intersection and are implemented in `core/`.

- **`gonthier`**: Gonthier's volumetric model. One force K·V at the volume centroid, with Gonthier's published friction
  (equations and sources in [`docs/gonthier-model.md`](docs/gonthier-model.md)). `gonthier-thesis` keeps the 2018 thesis
  form.
- **`distributed`**: the same foundation integrated point by point over the contact surface. Pressure K·ℓ·(1 − h·vn), Coulomb
  friction from each point's own slip, with a closed-form friction force and moment for a linear pressure on a triangle
  under a rigid slip field (the one new ingredient; derivation in the paper). The centre of pressure, spin and rolling come
  out on their own.
- **Baselines** from the literature, to isolate what is new: `distributed-vertex` and `distributed-centroid` (the friction
  quadratures of Hasegawa and Sato, and the one-point rule of PCM and Simbody) and `pcm`, the per-face elastic foundation.
  Formulations, sources and every departure: [`docs/baselines.md`](docs/baselines.md).

## Engines and native models

Drake 1.58, Chrono 10.0 and MuJoCo 4.0, each with the same force-law coupling and, as the comparison, its own contact
model configured by one documented rule for all scenarios ([`docs/scenarios.md`](docs/scenarios.md) §3): Drake
`hydroelastic` and `point`, Chrono `smc` and `nsc`, MuJoCo `soft` and `default`. `--contact native:<model>` selects one. The laws give the
same results on the three engines; the engine changes the cost, not the answer.

## The battery

33 scenarios, from a block on an incline to a ten-block tower, each with an error metric against its reference. A
classifies the reference as a rigid-body result, B an assumed pressure distribution, C the elastic-foundation model itself
(a consistency check, not an accuracy one). Twelve scenarios are a held-out set written before any law was run on them.
Every scenario runs a variant matrix: base, meshes of 32 and 128 segments, time steps from 2 to 0.1 ms, stiffness × 10 and
eight seeded perturbations. Statistics (pass rates, paired ratios with bootstrap intervals, performance profiles,
convergence slopes) come from `tools/stats.py`. The specification is [`docs/scenarios.md`](docs/scenarios.md).

## Limitations

What the battery shows, in the words of the revised paper (Sections 5 and 6; numbers in `results/stats.md`,
section "Robust paired ratios"):

- **Not better in general, and the comparison depends on how failures are counted.** With errors capped at 100 %, runs
  without a value counted at the cap, the four `pieces*` scenarios counted once and Holm's correction over 14 primary
  comparisons (`distributed` against `gonthier`, each against every engine's default native model, on A and on A+B),
  two survive, both on A+B: `distributed` against `gonthier` and against Chrono SMC (the second one close to the
  threshold). On class A the laws have the smaller error than each default native model in most scenarios and no
  difference is significant; where a body slides or rolls on one plane, Drake point and Chrono NSC are as accurate or
  more. The first analysis (uncapped, failures left out) is kept next to the robust one; no conclusion rests on it.
- **Class B is consistency plus a band.** The nominal references are the Winkler model's own pressure; `distributed`
  and Drake hydroelastic are never outside the band of admissible distributions, the point-contact models are in up to
  three of five scenarios. The battery did not record the sign of the error, so some runs cannot be placed.
- **The closed-form friction buys independence of the triangulation, not accuracy as such.** The battery's flat caps
  are fans from a rim vertex; on them the one-point and vertex rules lose 18 % and 25 % of a disk's spin torque at any
  number of segments, on a centre fan the one-point rule is within 0.04 %, and on well-shaped meshes both converge at
  second order (`uv run tools/ablation_triangulation.py`, `results/ablation_triangulation.csv`). The closed form is
  exact on every triangulation and under any cut of the bodies.
- **One finite-element reference, no experimental one.** The references are analytic; class C tests consistency with a
  Winkler foundation, not accuracy, and no recommendation rests on it. A static finite-element solution of `disk` and
  `bearing` (`uv run tools/fem/run.py`, `results/fem/README.md`, paper Section 5.4) places a continuum support in the
  band: the thin sleeve of `bearing` gives the Winkler cosine (the four foundation methods within 5 % of it, not
  ranked), the thick slab of `disk` behaves as a half-space with the rigid-punch pressure, and against it `distributed`
  and Drake hydroelastic stop 18 % late: a limit of the Winkler foundation on a thick support, not of the
  discretization. It is static, frictionless in the normal problem and covers two scenarios. The laws were developed on 21 of the scenarios and changed
  after the first run of the 12 held-out ones; the native models were configured by us, revised after first results on
  the development scenarios, and not reviewed by their developers (Drake point has corner spheres on boxes and one
  point under a disk). K was chosen so that the explicit coupling is stable at 1 ms; `bowl`, `trough`, `turntable` and
  `edge` mostly measure h and K.
- **Explicit coupling.** K·A·Σw·dt² < 2: a body held between two flat contacts needs dt < √(m/(K·A)) (0.25 ms in
  `massratio`, which is lost at 1 ms and holds from 0.2 ms), and the damping through a light body is bounded. Implicit
  integration with the force Jacobians is not done.
- **Rolling resistance of the damped foundation** makes long rolling drift (`turntable`, `bowl`, `trough`), by the
  amount the model predicts (`turntable`: +77 % predicted, +69 % measured).
- **One normal per pair of convex pieces**: `distributed` does not converge with the mesh on `journal`; a per-face
  foundation with local normals (`pcm`) and hydroelastic contact do better on curved conforming contact. Bodies must be
  cut into convex pieces that fill them without overlapping.
- **Friction-induced flutter on stiffer foundations (diagnosed, `docs/research/anomalies.md`).** A sliding face under a
  body with a raised centre of mass wobbles when μ·K·(π·R³/3)·(H/2) exceeds the rocking damping h·m·g·R²/4 times the
  rocking frequency √(K·I_A/I_t): above K ≈ 1.9e6 N/m³ for `disk`, with predicted growth rates (6 and 31 s⁻¹ at 3 K and
  10 K) equal to the measured ones (6.6 and 32). It is a limit of validity of the damped Winkler law with sliding
  friction, not of the coupling. Open: why `pcm` does not flutter, and how much of the `cone` and `bearing` errors at
  10 K is this and how much the facet sag.
- **The energy term of `energy` omits the contact spring (diagnosed).** With h = 0 the bounce is never damped, so the
  term varies irregularly with the step and the start for every law (`gonthier` 0.14–3.3 %, `pcm` 0.07–4.6 %); the
  3.1 % of `gonthier` at 1 ms is one such value, not a steady gain. Gonthier's normal force K·V·n is not conservative
  on faceted geometry (curl −K·(V/A²)·∇A×∇V), by an amount that was not isolated. Open: which change moved the nominal
  run from 0.16 % (first held-out run) to 3.1 % (not bisected).
- **Timings** are valid only from `scripts/bench.sh --timing` on an idle machine (`results/timing.csv`; `results/load.txt` records the machine and its load).

The full list with evidence is in [`docs/history.md`](docs/history.md).
